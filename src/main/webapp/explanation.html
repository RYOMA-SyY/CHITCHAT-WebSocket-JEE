Chat Application Logic Breakdown

This document details the internal workings of the WebSocket Chat Application. It focuses purely on the Java (Server) and JavaScript (Client) logic, excluding UI/CSS details.

1. Server-Side Logic (ChatEndpoint.java)

The core of the application relies on the Jakarta EE WebSocket API. The server acts as a central hub that manages connections and broadcasts messages.

1. The Endpoint Annotation

@ServerEndpoint("/chat")

This annotation tells the server (Tomcat) that this Java class is a WebSocket server. It listens specifically on the URL path /chat. Any connection to ws://domain/App/chat is routed here.

2. Managing Sessions (Connections)
private static final Set<Session> sessions = Collections.synchronizedSet(new HashSet<>());

We use a static Set to store every active user connection (Session). It is static so that it is shared across all instances of the class (global state). We use Collections.synchronizedSet to ensure "Thread Safety"—preventing errors when two users join close to the exact same time.

3. Message History (In-Memory)
private static final LinkedList<String> messageHistory = new LinkedList<>();

We store the last 50 messages in a simple Java List within the memory (RAM). This acts as a temporary database. When the list exceeds 50 items, we remove the oldest one (removeFirst()) before adding the new one.

4. Connection Lifecycle Events
  • @OnOpen: Triggered when a client connects.
    • Adds the session to the valid sessions list.
    • Immediately loops through messageHistory and sends all past messages to this specific new user so they are caught up.
  • @OnMessage: Triggered when the server receives a message.
    • Rate Limit Check: Checks a map of timestamps to see if this user sent > 5 messages in 5 seconds. If yes, it sends a private "System Alert" back and aborts.
    • History: If allowed, the message is added to messageHistory.
    • Broadcast: The message is sent to ALL active sessions in the sessions set.
  • @OnClose: Triggered when a user disconnects. Removes them from the lists to stop trying to send them messages.

2. Client-Side Logic (JavaScript)

The client runs in the browser and manages the bidirectional communication with the server.

1. Connecting to the Server
var protocol = window.location.protocol === "https:" ? "wss://" : "ws://";
var wsUrl = protocol + host + contextPath + "/chat";
ws = new WebSocket(wsUrl);

The code dynamically builds the WebSocket URL. It checks if you are on HTTP or HTTPS and switches to WS or WSS (Secure WebSocket) accordingly. It then opens a persistent connection to the server.

2. Handling Events
  • ws.onopen: Runs when the connection succeeds. We update the UI to show "Connected" and enable the input fields.
  • ws.onmessage: The most crucial function. It runs whenever data arrives from the server.
    • It reads event.data (the text sent by Java).
    • It checks for special prefixes like System: 🚫 to show alerts.
    • It parses standard messages Username: Message.
    • It detects special flags like [GIF] or image extensions (png, jpg) and renders an <img> tag instead of plain text.
  • ws.onclose: Runs if the server kicks us off or the internet drops. We disable all buttons to prevent errors.
3. GIF Search Logic (Tenor API)
fetch("https://g.tenor.com/v1/search?q=" + query + ... )

This is a standard HTTP REST call, not WebSocket.

  • We take the user's search text.
  • We call Tenor's public API URL.
  • When the JSON data comes back, we loop through the results and create clickable image elements.
  • Clicking an image calls sendGif(url), which sends a special text message: User: [GIF]https://....
